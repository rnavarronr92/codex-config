# Node.js and TypeScript review reference

Use for Node.js backends and TypeScript execution/build changes. Apply Fastify
and MCP sections only when those technologies occur in the reviewed path.
These are investigation prompts; report a defect only with a reachable scenario.

## Runtime and contracts

- Establish supported Node.js and package versions from manifests, lockfiles and
  deployment/CI configuration. Distinguish development runners from production
  execution; do not require a newer runtime merely because it exists.
- Check ESM/CommonJS, module resolution, emitted import paths and entry points
  against the actual build. Development aliases or a passing transpilation step
  do not establish that the emitted application can start.
- Treat type assertions, non-null assertions and static interfaces as compile-time
  claims. Follow external data through runtime validation, including coercion,
  optional fields and response serialization. Verify library behavior before
  asserting that a value is accepted or rejected.
- Native TypeScript execution/type stripping does not replace type checking.
  Compare the configured compiler coverage with application, scripts and tests;
  do not assume a development runner uses all `tsconfig` settings.

## Async work and resource ownership

- Trace returned/awaited promises, detached work and error propagation. Look for
  responses sent before required work, swallowed failures and rejections without
  a handler. Distinguish intentional background work with its own error handling.
- Check concurrency limits against pool capacity and ordering requirements;
  a `Promise.all` is not inherently wrong. Establish input bounds before claiming
  exhaustion or recommending batching.
- Inspect request-specific mutable state shared through singletons, closures or
  caches. Follow the actual interleaving before claiming cross-request leakage.
- Follow pool/client/stream creation through partial startup failure, disconnect
  and shutdown. Check release in failure paths and whether a request closes a
  resource still owned by the process or other requests.
- Identify synchronous I/O or expensive CPU/serialization work on reachable
  request paths. Require workload evidence for a performance finding; `async`
  alone does not establish that computation yields to the event loop.

## Fastify, when present

- Trace plugin registration/encapsulation and hook order to each affected route.
  Verify that validation, authentication and error handling apply in that scope.
- Check hook completion conventions: mixing callbacks with returned promises or
  continuing after an early reply can execute work twice or send another reply.
  Establish the behavior for the installed Fastify version.
- Compare configured validators/type providers with runtime input schemas and
  serializers. A schema/type declaration alone does not prove integration.
- Inspect response schemas for dropped required fields or exposed sensitive
  fields. Preserve the repository's status/error contract; do not move database
  work into schema validation as a generic recommendation.

## MCP contracts, when present

- Follow tool registration, input parsing, application operation and result
  adaptation. Check names, required/optional inputs and output schema compatibility
  with existing callers. Distinguish tool execution errors from protocol errors.
- Check structured results against the declared output schema and any companion
  content generated by the implementation. Do not treat an HTTP status or an
  OpenAPI description as proof of the MCP result contract.
- Follow request identity and resource ownership through server/transport reuse.
  Preserve the supported stateful/stateless model and SDK lifecycle; do not
  prescribe one server instance per request for every MCP implementation.
- For security-sensitive paths, use `security-review` and its MCP/OAuth reference
  when available; otherwise trace the same boundaries and disclose limitations.

## Verification and sources

Use existing scripts for type checking, tests, architecture checks and builds
only within the enclosing review's execution permissions. Inspect service/fixture
isolation first; a test name does not establish that it avoids business data.
Do not install packages or infer that missing tools mean the checks passed.
